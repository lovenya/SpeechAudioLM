# Cluster Migration

Use this skill when a project is being moved to a new cluster, HPC system, lab
server, or fresh environment. The goal is to preserve project state while
avoiding brittle transfers of environment-specific artifacts.

## Core Workflow

1. Inspect repo instructions and current handoff docs first:
   `AGENTS.md`, `README.md`, `CONTEXT.md`, `HPC_BEST_PRACTICES.md`,
   `PROGRESS_LOG.md`, `CHANGELOG.md`, and any migration-specific docs.
2. Check `git status --short` and recent commits.
3. Audit path-bearing configs and scripts with `rg` for old roots such as
   `/project`, `/scratch`, `/lustre`, `$HOME`, hard-coded model paths, cache
   paths, and scheduler account/partition names.
4. Classify every resource into one of:
   - **transfer exactly**: project data, handoff docs, non-public source, local
     patches, irreplaceable outputs;
   - **re-download**: public Hugging Face/GitHub model weights, metric
     checkpoints, public source repos, package caches when internet is available;
   - **recreate fresh**: venvs, compiled extensions, node-local caches,
     scheduler jobs, temporary outputs;
   - **optional transfer**: generated results/logs needed for continuity.
5. Identify public vs local source trees. For each external repo, record
   remote URL, commit hash, and whether local modifications exist.
6. Prepare a minimal transfer/download plan with exact old paths and intended
   new path variables.
7. Update docs/configs only after distinguishing durable project policy from
   cluster-specific notes.
8. Commit documentation/config updates if the user wants them available from a
   fresh clone.

## What To Transfer

Prioritize:

- repo working tree or GitHub clone;
- tracked and intentionally vendored handoff docs;
- datasets and manifests not recoverable from public sources;
- local source trees with uncommitted or non-public modifications;
- small config files, split files, reports, and project briefs;
- custom Codex skills needed by the new agent.

Use transfer tools that preserve symlinks and support resume, for example:

```bash
rsync -aH --info=progress2 SOURCE/ DEST/
```

## What To Re-Download

Prefer re-downloading public assets on the new cluster when internet, quota, and
time allow:

- Hugging Face model snapshots;
- public GitHub source repos;
- public metric checkpoints;
- package wheels and pip caches;
- model caches that can be regenerated by documented commands.

Record exact repo IDs, URLs, checkpoint names, and expected cache directories.

## What Not To Transfer

Do not recommend venv transfer as the primary path. Recreate venvs under the new
cluster's Python/CUDA/compiler/module stack because venvs often contain:

- absolute interpreter paths;
- compiled extensions tied to old system libraries;
- GPU/CPU architecture assumptions;
- stale cache paths.

Also skip node-local temp dirs, large transient package caches, and scheduler
state unless explicitly needed for debugging.

## New Cluster Setup Checks

Before running heavy jobs:

1. Define path variables such as `PROJECT_ROOT`, `SCRATCH_ROOT`, `DATA_ROOT`,
   `MODEL_ROOT`, and `CACHE_ROOT`.
2. Rewrite path-bearing configs and scripts to those roots.
3. Verify every configured file path exists.
4. Run unit tests or import checks.
5. Run dataset path/report validation.
6. Run dry-runs that do not load heavy models.
7. Run one-sample compute-node model smokes.
8. Run one metric backend smoke in its own env.
9. Run full baseline/eval only after small smoke passes.

## Scheduler And Resource Notes

- Do not assume the new cluster uses the same scheduler, accounts, partitions,
  modules, GPU names, or internet policy.
- Treat submission scripts as templates until audited.
- Keep resource monitoring if available.
- Use observed smoke runtime and peak memory/VRAM to size production jobs, with
  a modest buffer instead of defaulting to long allocations.

## Codex Knowledge Transfer

If project-specific Codex skills were used, vendor them into the repo as:

```text
codex/skills/<skill-name>/SKILL.md
```

Document how to install them on the new cluster:

```bash
mkdir -p ~/.codex/skills
cp -a codex/skills/<skill-name> ~/.codex/skills/
```

The new agent should read repo instructions and handoff docs before changing
paths, environments, datasets, splits, or scheduler scripts.

## Output Shape

For a migration audit, lead with:

- readiness verdict;
- blocking issues, if any;
- transfer exactly;
- re-download;
- recreate fresh;
- optional transfer;
- config paths to rewrite;
- first validation commands on the new cluster.
