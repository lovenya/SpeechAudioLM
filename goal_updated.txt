# SpeechAudioLM Ultimate Goal

## Operating Rules

- The agent must finish the migration, model/env setup planning, metric support, and cascaded baseline work described in this document.
- The agent must not submit model-download jobs, download weights, create environments, or run setup commands that burn quota unless the user explicitly instructs the agent to do so.
- The agent should prepare exact command batches for the user to run. The user will execute those commands and report completion or errors.
- Command batches should be grouped for parallel terminals when setup/download tasks are independent. The user currently has five parallel terminals available.
- The agent must debug from evidence supplied by the user: command output, logs, errors, manifests, Slurm accounting, and resource summaries.
- The agent must not run polling loops. For compute jobs, checks should be bounded: at 5, 10, and 15 minutes, then every 30 minutes after that, then final logs/accounting.
- The agent must keep referring to repository docs because they contain migration/debugging context from earlier work.
- The agent must keep updating handoff/docs after verified milestones, using the repository documentation workflow.
- After each milestone, the agent should get progress reviewed by a subagent before committing tracked code/docs.
- The agent may commit tracked source/config/docs after review, but must never commit datasets, audio, checkpoints, downloaded weights, venvs, caches, logs, outputs, wandb runs, secrets, or other generated artifacts.

## Resource Policy

- TamIA H100 jobs should use one H100 node only: `--gpus=h100:4`.
- The agent must not request more than one node for now.
- The agent should avoid explicit CPU/RAM requests unless evidence shows they are required. On TamIA, one H100 node already provides the full 4-GPU node.
- The main resource dimension to size is walltime.
- Walltime should be based on observed smoke/runtime plus about 25%.
- If TamIA rejects sub-hour jobs, use the minimum accepted time and document that scheduler constraint.
- Resource monitoring must be enabled for compute jobs when available.
- The agent should review resource-monitor summaries and Slurm accounting (`sacct`, `MaxRSS`, elapsed time, allocated TRES) before sizing larger jobs.

## Phase 2: Complete Metrics

Confirm or add support for these metrics:

- `wer`
- `asr_wer`
- `dwer`
- `mace`
- `spider`
- `aac_clapsim`
- `clap_score_t2a`
- `kl_passt`
- `fad`
- `kad`
- `inception_score`
- `utmos`
- `dnsmos`

Metric completion requirements:

- Each metric must run through `evaluate.py`.
- Before using `submission_scripts/run_eval_available_metrics_array.sbatch`, audit and likely reduce the smoke resources. It currently requests `--time=04:00:00`, `--cpus-per-task=48`, `--mem=0`, and `--gpus=h100:4`; this is too broad for a one/two-sample metric smoke unless Slurm/accounting evidence justifies it. Prefer one H100 node only, no explicit CPU/RAM override unless required, and walltime from observed runtime plus about 25%.
- For tiny metric validation against existing manifests, `submission_scripts/run_eval_smoke_existing_manifests.sh` is the safer starting point inside an already allocated compute session because it limits to `--max-samples 2` and does not submit a job array.
- Metric smoke job `309048` failed immediately in `audioldm_eval` because the TamIA clean Torch cache has VGGish checkpoint files but not the Torch Hub source repo `harritaylor/torchvggish`; compute nodes then tried GitHub and timed out. Cache that Torch Hub repo under `$SALM_SCRATCH/cache/metrics/torch/hub` on an internet-capable node before expecting `fad,inception_score` to pass.
- `submission_scripts/run_tamia_eval_smoke_retry_manifests.sbatch` now isolates metric backend groups and continues after failures, so one missing backend cache does not hide the status of KAD, stable-audio-metrics, Whisper, or UTMOS.
- Import-only checks are not enough for completion.
- Each metric should produce per-sample or corpus outputs as appropriate.
- Backend logs should be inspected when a metric fails.
- DNSMOS is currently the main missing metric addition and should use a dedicated backend/env if needed, with cached ONNX assets under the clean migration root.
- DNSMOS is already allowed for generated-speech tasks in `configs/task_metric_map.json`, but it is not executable yet because `configs/eval_metrics.json` has `backend: null` and `evaluation/runner.py`/`scripts/eval_backend_worker.py` do not dispatch a DNSMOS backend.
- DNSMOS implementation should add a `torchmetrics-dnsmos` backend entry in `configs/eval_metrics.json`, add the backend to the external-metric dispatch table, add a worker branch/function that calls TorchMetrics DNSMOS on each generated audio file, and report per-sample `dnsmos` values plus backend metadata.
- DNSMOS setup validation should use `scripts/eval_backend_smoke/smoke_dnsmos.py` first to confirm TorchMetrics imports and cached ONNX assets exist, then run `evaluate.py --metrics dnsmos` on a one-sample generated-speech manifest.
- The expected clean-root DNSMOS asset paths are `models/metrics/dnsmos/DNSMOS/model_v8.onnx`, `models/metrics/dnsmos/DNSMOS/sig_bak_ovr.onnx`, and `models/metrics/dnsmos/pDNSMOS/sig_bak_ovr.onnx` unless the final backend documents a different TorchMetrics cache layout.

## Phase 4: Modular Cascaded Baseline

Build a modular ensemble/cascaded baseline with selectable stage backends.

Required modules:

- ASR module
- Audio captioning module
- Text-to-text reasoning module
- Text-to-audio generation module
- Text-to-speech generation module

The CLI should allow backend selection per stage, for example:

- `--asr whisper` or `--asr qwen3_asr`
- `--captioner audio_flamingo_next` or `--captioner qwen3_omni_captioner`
- `--text-model qwen3_32b` or `--text-model llama3_3_70b_instruct`
- `--tts f5_tts`, `--tts cosyvoice3`, `--tts qwen3_omni`, or another supported TTS backend
- `--t2a tangoflux` or `--t2a audio_omni`

Output/data-flow requirements:

- JSON output is acceptable and preferred for intermediate stage artifacts.
- Each stage should write inspectable intermediate JSON.
- Stages should be runnable separately when environments are incompatible.
- Final outputs should be compatible with the existing baseline/evaluation flow.
- At least one complete A2S cascade must work.
- At least one complete S2A cascade must work.
- Failed optional backends must have documented blockers.

Current baseline evidence and remaining modularity gap:

- `baseline.py` currently exposes backend/task execution through `--model` and `--task`; it does not yet expose independent stage selectors such as `--asr`, `--captioner`, `--text-model`, `--tts`, and `--t2a`.
- `audio_omni` currently contains backend-specific A2S/S2A cascades and records a `stages` array in `model_extra`; this is useful smoke evidence but does not satisfy the modular selectable-stage baseline requirement by itself.
- `qwen3_omni` A2S currently skips audio understanding and uses the paired `speech_text` as the intermediate transcript before TTS; it is a baseline shortcut, not a full A2S cascade.
- `baselines/README.md` already requires component-specific manifests for evaluable intermediate stages, but the shared run writer currently appends only the combined final-output manifest. The modular cascade implementation must add or otherwise produce component manifests, for example S2T/A2T intermediate manifests plus final S2A/A2S manifests.
- Completion requires real compute-node end-to-end runs for one A2S and one S2A modular cascade, with successful final manifests and inspectable intermediate JSON/manifests.
